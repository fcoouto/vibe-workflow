### B1 resolution — Codex session-file counts only

**Decision:** read token counts from Codex session files (`$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<timestamp>-<thread-id>.jsonl`). Keep only numerical `token_count` rows. Reuse the path guards in `runtime/adapters/codex.py:guarded_child_lineage`: path under `$CODEX_HOME/sessions`, resolved without links, private file, name bound to the thread ID, first row `session_meta` with matching `id`.

Rules:

- **Finding the file.** A thread ID alone does not give the path, and a thread may start days before the task. List date folders backward from the cutoff date (plus one day for time zones) for at most 30 days, and match the full name form `rollout-YYYY-MM-DDTHH-MM-SS-<thread-id>.jsonl`, anchored at both ends so one thread ID can never match another thread's file. Stop at the first folder with a match. Open no other file. No match within 30 days (`thread_file_not_found`) or several matches are a gap. This is a name lookup, not a content scan.
- **Reading.** The existing 512 KiB / `CANONICAL_MAX_ROWS` reader is too small for long sessions. O3 adds a streaming line reader with fixed limits: 64 MiB per file, 1 MiB per line, the existing deadline. Skip without parsing any line that does not contain the bytes `"token_count"`, `"session_meta"` or `"turn_context"`. A matching line over the line limit, or a file over the file limit, is a gap. An unterminated last line is ignored, because the file may still be written.
- **Content.** From matching lines keep only the row timestamp, `token_count` `info`, `session_meta.id`/`timestamp`/`cli_version` and `turn_context` model/effort. Drop each parsed row and its raw bytes immediately. Never retain, return, log or export message text, tool input/output or paths. Errors use fixed codes and never include line content. Consent text discloses that the reader opens files that also contain conversation text.
- **Version gate.** Accept only `cli_version` values in a qualified-version set held by the source module. It starts empty; O3 adds `0.167.0` only after real-file qualification. Any other version reports `source_version_unqualified` and no counts.
- **Counting.** `info.total_token_usage` is cumulative per thread: upstream adds each response's `last_token_usage` to it. Task usage per thread = final total at cutoff minus baseline total at task start. A thread whose `session_meta` time is after task start has baseline zero. Never sum `last` values or successive totals. Identical consecutive `info` rows are one observation (upstream re-emits counts after rate-limit updates).
- **No double counting.** Each thread's total covers only that thread's own model responses; child threads have their own files. O3 must confirm this on real files. If a parent total includes child usage, O3 stops and reports instead of subtracting.
- **Gaps, never zeros.** These checks apply to `token_count` rows from the baseline row through the last row at or before cutoff. Report an explicit gap when: `info` is null after a row with non-null `info` (with a zero baseline, null rows before the first non-null row mean no usage yet and count as zero; ruling of 12 November 2026 after O3 review, to confirm on real files); any counter decreases; `total_tokens` equals `model_context_window` (upstream `set_token_usage_full` overwrites the total when the context window is exceeded); a counter field is absent; the file cannot be read; rows lack a usable time for baseline/cutoff placement; the thread was resumed or forked in a way O3 has not qualified. A gap leaves that thread's usage unknown.
- **Participants.** O3 does not look up threads; the integration hook passes them in. The coordinator thread is the task's Codex `session_id`. Worker threads come from D6 assignment receipts (`native_identity.worker_id`, `runtime/delegation.py:2036-2041`). Reviewer threads come from D5 review receipts in `runtime/evidence.py`. The integration owner adds `task_threads(scope, task) -> [{thread_id, role}]` in `runtime/evidence.py`, names the reviewer field in this section before coding, and tests it. Check runs and coordinator operations have no model thread and add no usage. An expected thread with no readable file makes coverage incomplete.
- **Model provenance.** `model_settings` lists the distinct `(model, effort)` pairs from the last `turn_context` row at or before task start plus every later one up to cutoff, in first-seen order, labelled `configured`, not served. Charges stay unknown for subscription use.
- **Timing.** Task start is the existing task record's `lifecycle.created_at`, converted to UTC using the unit its writer in `runtime/state.py` uses; the integration test pins that unit. A task without `lifecycle.created_at` is a gap for every thread. The integration hook captures cutoff as the current UTC time immediately before calling O3. Both are passed to O3 as timezone-aware UTC `datetime` values. Usage after cutoff, including the rest of the verifying turn, is not counted and is reported as the `after_cutoff` limitation. Placement uses row timestamps if 0.167.0 files carry them; O3 confirms this. Without them the thread is a gap.
- **No new process.** The reader runs only inside the completion seam. No listener, daemon, polling, model call or account query.

### B2 resolution — one upload after settlement, then adjustment records

**Decision:** settle the task total locally, upload it once, and express any later change as a separate adjustment record. Langfuse sums all records for the task, so the dashboard total reaches the corrected value without updating an uploaded record.

Rules:

- **Owner and writes.** Export state lives in the existing evidence owner's private task receipt, not a new store. `runtime/evidence.py` gains `read_export_state(scope, task_ref, destination_key) -> dict` and `write_export_state(scope, task_ref, destination_key, *, expected_revision, state) -> dict`. A write whose `expected_revision` is stale fails, so two concurrent hooks cannot both apply the same change. State: `{revision, correlation_id, reconciled_revision, exported_totals, records: [{export_id, sequence, kind, delta, correction_of, outcome}]}`. `correlation_id` is a random opaque ID created with the first upload and reused by every adjustment for that task and destination.
- **Identity.** Before each POST, generate a random opaque export ID and write it with outcome `pending`. Bind it to destination, Langfuse project and task. Never derive IDs from labels, paths or hashes of user data.
- **Delivery outcomes.** One span per POST. `accepted`: 2xx with no rejected spans in `partialSuccess`. `rejected`: nothing was stored. That means the connection failed before any request bytes were sent, a 2xx response reports the span as rejected, or a 4xx other than 408 and 429; resending the same ID is then allowed. `uncertain`: everything else, including timeouts after sending, 408, 429 and 5xx. Never resend `uncertain` automatically.
- **Uncertain blocks further export.** While any record for a task and destination is `uncertain`, plan no further upload or adjustment for that pair. Status shows it. The user resolves it explicitly with the `resolve-export` action: `landed` (seen in Langfuse) marks it accepted; `missing` marks it rejected and allows resending the same ID, with a duplicate warning.
- **What is exported.** Only results with `verified` true and `admission_mode` `"ordinary"`. Unverified and qualification-mode results export nothing.
- **Corrections.** `exported_totals` sums accepted records only. A later reconciliation produces one adjustment record with a new ID, the delta (new total minus `exported_totals`), `correction_of` = the first export ID and the next sequence number. The reconciliation carries `reconciled_revision`, the verified task revision (`result["task"]["revision"]`, an integer). The planner refuses one whose value is not greater than the stored one, so a stale result cannot overwrite a newer one. Example: 100 accepted, corrected to 120, adjustment `+20`, sum 120.
- **Negative deltas.** Langfuse's acceptance of negative usage values is unqualified. Until O6 proves it, record a negative change locally as a gap and do not export it.
- **Restart.** After a restart, `pending` without an outcome becomes `uncertain`. Nothing re-sends on startup.
- **Payload allow-list.** Each span carries only: export ID, opaque task correlation ID, `kind` (`total`/`adjustment`), sequence, `correction_of`, the six counters, coverage (`complete`/`incomplete`), gap codes, Codex CLI version and configured model/effort. Nothing else.
- No score exporter, deletion or alternate provider.

**Integration rulings (12 November 2026).** `runtime/evidence.py` (8,505 lines) and `runtime/delegation.py` (3,369 lines) are exactly at their fixed ceilings in `scripts/validate.py`, so integration adds no code to them. **User decision:** upload state lives in the observability folder, not the evidence store: one private file per task and destination under `<state_dir>/observability/exports/`, written through the existing settings private-store code, with compare-and-set revisions; `export_state` is stored exactly as O5 returns it. The hook runs only in the `scripts/workflow.py` `evidence verify` branch after `verify_completion` returns; `verify_linked` has no public caller today, and any future caller must call the same hook per member after the linked operation returns. It acts only when the verification is an ordinary verified completion, this folder's Project record has collection on and lists the repository, and the checkout connection is enabled; otherwise it reads nothing more. It saves `pending` before each POST and the outcome after. New CLI actions `export-status` and `resolve-export` let the user see and resolve uncertain uploads. Unresolvable worker or reviewer threads block the upload (`participants_unresolved`).

**O5 rulings (12 November 2026, from current Langfuse docs).** Langfuse stores flat `langfuse.observation.usage_details` unchanged and treats every key as a separate bucket ([token and cost tracking](https://langfuse.com/docs/observability/features/token-and-cost-tracking.md), snapshot SHA-256 `0b9f9ec03b5e09fb0fb0595fbb162dd8fefbb97ea643ea044de4f4f0fa0be2b7`; [OpenTelemetry mapping](https://langfuse.com/integrations/native/opentelemetry.md), `96337464be840b7a17f1d7c74b494de9402d9d476070b31df76159d169fff4f4`). Codex counters are taken as inclusive (input includes cached and cache-write tokens, output includes reasoning tokens), pending real-file confirmation. Export maps them to `input`, `input_cached_tokens`, `input_cache_write_tokens`, `output`, `output_reasoning_tokens`, `total`, and skips locally (`usage_inconsistent`) when a bucket is negative or `input_tokens + output_tokens != total_tokens`. Spans are `generation` observations without a model name or cost, so Langfuse never infers API prices for subscription use; configured model/effort go to metadata only. Export state changes through pure helpers (`record_outcome`, `recover_pending`, `resolve_uncertain`); the stored `reconciled_revision` advances only on acceptance.
