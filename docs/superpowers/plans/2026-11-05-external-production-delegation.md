# External Production Delegation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let native coordinators use suitable, authorized OpenRouter text proposals for bounded production changes, including basic configured checkouts, when capacity and the complete cost of an accepted result justify delegation.

**Architecture:** Reuse shared offline selection, scoped packet construction, OpenRouter consent and the existing proposal attempt store. External models return candidate code, patches, tests or documentation as text; native agents decide and invoke every tool, integrate changes, verify behavior and obtain distinct independent native review. Start with one-shot proposals and preserve native takeover; external repair is a later evidence-driven extension of the existing attempt owner.

**Tech Stack:** Python 3.11+ standard library, unittest, Markdown contracts, existing authenticated OpenRouter MCP connector, existing native Codex tools and reviews. No new dependency, executor, service or database.

**Spec:** [Prior shared external design](../specs/2026-11-05-shared-external-delegation-design.md), read with the explicit amendments below. After source reconciliation, consult `docs/superpowers/specs/2026-11-05-workflow-template-design.md` at pinned source `d73252a77d1e784f8a7d6f637bc661467485178d`. That file is absent in the original authoring checkout; do not invent a replacement or copy installed package artifacts.

## Global Constraints

- Planning was explicitly requested from Astra with user-selected **option 1: the native model decides every tool action**. This authorizes this plan, not implementation, installation, configuration, inference, source transmission, spending, commits, merges, releases or publication.
- The prior shared design remains an unapproved historical draft. This plan does not approve its broader OpenAI API scope. Deliver the OpenRouter proposal route first; retain other integrations and reusable shared eligibility without broadening their permissions.
- Preserve coordinator model, reasoning, provider, authentication, subscriptions, user customizations and native review selection. External output has no local tools, repository write access or authority to execute commands, including read commands.
- Apply binding restrictions, revocations and explicit choices first. Otherwise honor the approved local profile's exact assessment, language, complexity, context, budgets, capacity and verification, including bounded waiting and native fallback. Local congestion/failure is never a reason to spill that assignment externally.
- Preserve saved enablement, task/source/exclusion/destination/effort/funding permissions and their valid existing evidence. Ask only for missing authority; no new recurring approval, mandatory credit preflight, arbitrary dollar cap or compulsory expiry. OpenRouter enforces spending limits.
- Credit availability is funding, not suitability. Preserve unknown charges, in-flight outcomes, exact retry ownership, output/time bounds and original shared task budgets.
- Native acceptance includes independent requirements/checks and a distinct native reviewer of the exact candidate. External self-verification and external-authored tests alone cannot establish acceptance.
- Keep each skill entry point within 150 words. Define each wrapper rule once. Use `skill-creator` for instruction edits; maintain source-to-contract coverage and test selective loading.
- No universal schema, mandatory task form, extra ledger, new model catalog, numeric capability score, subscription-to-dollar conversion or observability collector/dashboard. Reuse current record owners.
- Preserve authoring WIP and installed packages. No implicit commits, merge, release archive, publication or real settings changes. Future execution uses separately granted scope; this document grants none.
- Validate with `python3 -B scripts/validate.py`. Report package validation and observed client execution separately. Planned checks below have not run.

## Review Focus

1. A basic configured checkout has workers-only saved consent: proposal support must not silently add a route, enable it or create managed runtime state. Task 2 exercises the boundary.
2. Reconfiguration, disable or source changes occur between preparation and dispatch: stale packets must not send, and an already issued grant must retain truthful uncertain accounting. Tasks 2 and 4 exercise this boundary.
3. A plausible candidate embeds tool instructions or weakens its own tests: native tool decisions and independent baseline checks must still reject it. Tasks 4 and 5 exercise the behavior.
4. Local capacity is busy or a model is inexpensive but unsuitable: neither local preference nor capability/context/review prerequisites may be bypassed by a cost argument. Tasks 3 and 5 exercise selection.
5. Accepted-only history or missing native usage creates apparent savings: failed, interrupted, repaired and takeover work must remain visible, unknown values must stay unknown, and comparable task classes must be disclosed. Tasks 4 and 5 exercise accounting.

## Compatibility, disable and recovery

Existing settings versions, explicit no-expiry/funding choices, manual proposal authority, workers permission and histories survive. Reading/installing new code performs no migration. Basic proposal configuration uses the existing basic store and bound checkout identity; selecting managed runtime later retains the existing separate-store/no-migration behavior. Changed/replaced authority is reconciled through its owner, never repinned by delegation.
