# OpenCode

Load this file only when a task implements, tests or diagnoses Smart Routing on OpenCode: the [adapter](../runtime/adapters/opencode.py), the [routing plugin shim](#pre-transmission-shim), or a routed OpenCode launch. OpenCode titles have their own [title contract](workstreams-titles.md#opencode-sessions). OpenCode is not an onboarding or startup client, and nothing here enrolls a project or qualifies OpenCode for the workflow.

## What the adapter does

The adapter turns OpenCode payloads into small, typed records for the routing command. It is pure: it reads no files, starts no process and makes no network call. It covers OpenCode 2.2.6, the version the probes ran on.

- `normalize_hook(hook, payload)` covers the four hooks routing uses: `model.request`, `tool.execute.before`, `permission.evaluate` and `shell.create.before`. The plugin passes the hook name because payloads do not carry it. Output includes the session and message IDs, agent, tool and tool class, request kind (`primary`, `title`, `compaction`, `generate`, otherwise `unknown`), the requested model, route identity, and for a subagent call the agent and any requested `provider/model#variant`.
- `normalize_event(event)` covers lineage and usage events: session created (with parent and agent), step started and ended (model, tokens, cost, rate-limit telemetry), usage updated, model selected and execution outcome. Each durable event keeps its per-session `durable_seq` so a gap can be detected. Other event types come back as `kind: "unknown"` with their sequence number and no body.
- `normalize_message(message)` covers stored messages: model, variant, finish, tokens, cost, `native.rateLimit` windows, and subagent tool calls with their child session.
- `probe(capabilities)` classifies already-observed capabilities without launching OpenCode (see below).

What never leaves the adapter: prompts, message and reasoning text, compaction summaries, tool output, command text, and header or environment values. Headers become a list of names, a base URL becomes its origin, and environment variables become names, with likely credential names listed so the shim can strip them. Command text yields only best-effort launch markers such as `opencode`, `claude` or `curl`.

Missing data stays unknown (`None`), never guessed. Field names carry units: times end in `_ms` (epoch milliseconds), rate-limit resets in `_s` (epoch seconds), and utilization is `utilization_fraction` (0–1); a value above 1, such as a percentage, stays unknown. Task, stage and attempt are not in OpenCode payloads; the dispatch record binds them by message ID. Hooks carry no parent session; it comes from the session-created event or a stored subagent call. A malformed, oversized or wrongly typed payload raises `AdapterError` with a fixed reason that never repeats the payload. Session, message, event and tool-call IDs must match their expected patterns.

## Route identity

Route identity is the provider, model alias, requested variant and catalog family. The resolved model is always `unknown`, because OpenCode stores only the requested alias. The harness is `claude-agent-sdk via opencode` for the Claude Agent provider; other providers are named by provider.

**A listed model is not an entitled model.** After OpenCode 2.2.6's "Sign in with ChatGPT", the `openai` provider lists a fixed set of 18 ids without checking the account. OpenAI then refused a listed one (`gpt-5.5`) with HTTP 400 `model_not_found`: "not supported when using Codex with a ChatGPT account" (observed 10 November 2026; [live report](../docs/smart-routing-qualification.md#chatgpt-attempts-5-and-6)). The ChatGPT route supports only a subset; OpenCode's own rule for its legacy Codex sign-ins enables `gpt-N.M` above 5.5 only. A route admitted from the listing alone can still fail upstream; treat that refusal as a route failure, not as a reason to retry other routes blindly.

## What can be enforced

The [capability matrix](../docs/smart-routing-capability-matrix.md#opencode-enforcement-p01-p05p08) owns which paths can be blocked before sending, which cannot, and the user's decisions about them. `probe` applies those facts to observed capabilities and returns:

- `unsupported`: fixed reason codes, always including the matrix's unsupported paths (`ALWAYS_UNSUPPORTED` in the adapter), plus any that apply to this host.
- `managed_launch: "refuse"` when the `routing.health` check failed or a required hook is missing; otherwise `"allow"`.
- `enforcement_profile: "enforced"` only when the launch is allowed, the version is the qualified one, `shell` is denied, MCP tools, Code Mode `execute` and `webfetch` are each denied or narrowed, `image_generation` is denied and `config_edit` is denied or narrowed to exclude the [config paths](#image-generation-and-configuration-edits-s33d). Otherwise `"advisory"`, with `image_generation_unmediated` or `config_edit_unmediated` when one of the last two is missing or weaker. Allowing `shell` in any form, even a narrow pattern, keeps the profile advisory.

`probe` does not judge what counts as narrow. The launcher reports each tool's state from the worker profile's policy rules, and that profile owns the allowed list. It reports `image_generation: "deny"` and `config_edit: "deny"` when `routing.health` answers `ok` and lists both in `managed_denies` (the shim applies them) or its policy rules deny them; a shim that does not list them leaves the profile advisory. `config_edit: "narrow"` is the launcher's own claim that its rules exclude the [config paths](#image-generation-and-configuration-edits-s33d), trusted like its other tool states; `probe` does not check it.

## Pre-transmission shim

[`opencode_plugin.ts`](../runtime/adapters/opencode_plugin.ts) is an OpenCode V2 server plugin with no dependencies; it runs in the runtime embedded in `opencode`. It holds no selection or funding logic: it asks the routing command and enforces the answer. It never logs, and its errors carry only a fixed reason code (`routing: blocked (<reason>)`), never prompts, headers, environment values, dispatch authorities or other payload content. Its field extraction mirrors the adapter, and the tests compare the two.

### Managed and interactive sessions

Only managed sessions are protected (user decision in the capability matrix). A session is **managed** when a managed launcher attached it in this plugin instance with `routing.attach`, or when its parent chain reaches an attached session. A session is **pending** when its ID has the shape of a ledger-derived ID (`ses_` and 32 lowercase hex characters) and an open attempt of the ledger owns it, or when its parent chain reaches such a session, and nobody has attached it here yet. A session is **closed** when its ID is a finished attempt's derived ID. Every other session is **interactive**: the shim sends no check, starts no child process and blocks nothing for it, even when the routing command is missing or broken.

Pending sessions are blocked until the launcher attaches them (`attach_required`): model requests and subagent spawns throw without a check and `webfetch` is denied. A closed session, and every session recorded under it, has its model requests and spawns blocked (`attempt_closed`), also after the launcher detached the root while subagents still ran. "Recorded" means two things. Sessions recorded as managed descendants while the root was attached are kept past detach (at most 4096, oldest forgotten first), and any session whose chain reaches one of them is blocked as well. Parent links from creation events after detach live only in the 4096-entry parent cache; once a link is evicted there, only those kept records and the closed sessions protect what lies below it. This relies on the same assumption about derived-shape IDs as below. Neither kind strips shell credentials or turns on `session.get` lookups; only an attached root does, so a stale entry can never break interactive work. This only adds protection: it stops a worker that reaches the server API from running a session under an open or finished attempt's derived ID before or after its launcher.

On `session.created` for a session it does not know, and on a hook for one, the shim asks the routing child a read-only `check` with only that `session_id` (see [the `unmanaged` answer](#the-unmanaged-answer)). It asks only about derived-shape IDs. It assumes OpenCode's own IDs never have that shape: the 2.2.6 server generated 26-character mixed-case bodies for sessions and messages in the [live qualification](../docs/smart-routing-qualification.md) (n=1 run), never `ses_` and 32 lowercase hex. If the assumption holds, interactive sessions are never asked about. Each question is shared while in flight. Creation events and hooks each have at most 8 questions in flight: past the event limit a creation is not asked about (and nothing is remembered, so its first hook asks), and past the hook limit the hook's session counts as unmanaged for now. A hook waits for a question at most one request budget (about 500 ms, plus the start-up allowance after a spawn). Answers:

- `authority_required`, `dispatch_required`, `attempt_uncertain` or `hold_state_unsupported` (an open attempt owns it): pending, even when the answer arrives late. A pending entry lasts 5 minutes, then the ledger is asked again. At most 1024 are recorded; beyond that a session is still blocked when asked about and is asked again next time.
- `attempt_closed`: closed, remembered for up to 1024 sessions (oldest forgotten first; a forgotten one is asked again). A finished attempt that has aged out of the ledger answers `unmanaged` instead, so its session then becomes interactive.
- `unmanaged`, a timeout and any store or request error (for example `ledger_absent`): interactive, remembered for 5 s. The hook limit: interactive for now, not remembered.

Attaching a pending session makes it a root and its recorded pending children its managed descendants. After detach a derived session the ledger still knows is pending again (or closed once the attempt finished).

The shim learns parents from `session.created` events. A new session whose parent is already attached or already a managed descendant becomes a **managed descendant**, at any depth; these records are never evicted. That is the only evidence a session is managed besides attachment: a session created while something is attached but under any other parent is interactive. For a session it has not recorded, the shim walks the parent chain using a cache of seen sessions and, only while a root is attached, `session.get` (at most 8 lookups of about 300 ms each per question; a failed lookup is remembered for 5 s, so it does not wait again). The session is managed if the chain reaches a root or managed descendant. Otherwise it is interactive: a missing or invalid session ID, a root, a cycle, a chain that cannot be determined, and a chain longer than 64 sessions. An attached session counts as a root.

Each attached root has its own budget of 256 recorded managed descendants, so one attempt's tree never limits another's. When a root's budget is used up, its managed subagent spawns are blocked (`descendant_limit`). A descendant created beyond that budget by another path, such as the API, blocks every session of that root with the same reason until the root is detached. The instance also has a memory ceiling of 4096 recorded descendants across roots: at the ceiling only new managed descendants, and spawns, of the root creating them are blocked. Detaching a root clears its descendants, count and blocking. Interactive sessions are never affected.

Attachments, with their dispatch authority, live only in the plugin instance's memory, and each project directory spelling gets its own instance. A managed launcher therefore uses the session's canonical directory (symlinks resolved) for every call below. Attaching through another spelling of the path reaches a different instance and protects nothing (observed).

### Handshake

A managed launch runs these steps in order and refuses to send if any of them fails:

1. `scripts/routing.py prepare` admits the attempt (and creates the ledger).
2. `routing.health` answers `ok`.
3. `scripts/routing.py dispatch` returns `dispatched` with the `authority` token and the derived `session_id` and `message_id`. The launcher keeps the token in memory for the attempt and never logs or stores it.
4. `routing.attach {session_id, attempt_id, authority, funding_pool, model, deny_actions?}` for the attempt's own derived session (never a child; children are learned from creation events). The shim verifies the token and the session's ownership through the child before it records anything.
5. Only after `attach` returned, the launcher creates the session and sends the prompt with the derived IDs. Every `check` the shim sends for that session and its child sessions carries `attempt_id`, the hook's own `session_id` and the token as `authority`.
6. After the attempt, in this order: re-read the sessions (see [Wiring](#usage-accounting-and-resync)), call `routing.descendants {session_id, attempt_id, authority}`, account with that answer, send `record complete`, then `routing.detach {session_id, attempt_id, authority}`. `descendants` answers only while the root is attached, so it must come before `detach`.

What the shim forwards to the routing child is limited to the request facts below, the attempt ID, the session ID and the token; the token goes nowhere else (not to OpenCode, not into an error, health or RPC result). If the plugin instance restarts during an attempt, the launcher attaches again with the same token; a `detach` refused because the restarted instance has no attachment needs no retry.

### What the shim does for a managed session

- `model.request`: checks the request with its kind (`primary`, `title`, `compaction` or `generate`). An unknown kind or a malformed model blocks without a check.
- `tool.execute.before` for `experimental_image_generate`: throws `image_generation_denied` without a check (see below).
- `tool.execute.before` for `subagent`: checks the spawn with kind `subagent` and the requested `provider/model#variant`. Managed spawns must name their model: a spawn without one (`subagent_model_required`) or with a malformed one blocks without a check. A route without a variant never matches an admission, because the admitted identity includes it.
- Every other tool, including MCP and Code Mode nested calls: no check. The worker profile's policy deny rules govern them; see [What can be enforced](#what-can-be-enforced).
- `permission.evaluate`: sets `webfetch`, any action listed in the attachment's `deny_actions`, image generation and edits of config paths (below) to `deny`, with the shim's message; an action that is already denied keeps its message. It only tightens; a configured `deny` is final and never reaches the hook.
- `shell.create.before`: the hook carries no session ID, so while any session is attached in this instance every shell that passes this hook (the `shell` tool and `/shell`) loses its environment variables whose names look like credentials. A command's `` !`cmd` `` expansion does **not** pass the hook and keeps the full environment (observed 9 November 2026: a dummy credential-like variable was visible and no `shell.create.before` record existed; [live report](../docs/smart-routing-qualification.md#live-probe-run-descendants-and-s33d-harness-85ae5f4)), so interactive or user-invoked commands in an attached instance expose credentials. The rule is the adapter's `credential_name`: after splitting camelCase (`githubToken`, `dbPassword`) and, for unusual names, punctuation, a name matches when one of its `_` segments is an API key, key, token, secret(s), password, `PASSWD`, `PASS`, passphrase, credential(s), `CREDS`, auth, `OAUTH`, cookie, private, `JWT`, `PAT`, `ACCESSKEY`, `SECRETKEY`, DSN, connection string or a database, Redis, MongoDB, Postgres, MySQL or AMQP `_URL`/`_URI`, or when it ends in `PASSWORD`/`PASSWD` (`PGPASSWORD`) or `_PWD` (`MYSQL_PWD`, but not `PWD`). Ordinary names such as `PATH`, `HOME`, `PWD`, `TERM`, `EDITOR`, `GIT_AUTHOR_NAME`, `npm_config_cache` and `TOKENIZERS_PARALLELISM` stay. Interactive shells in the same instance lose them too for that time; for example `SSH_AUTH_SOCK` goes, so git over SSH fails in that instance until the attached sessions are detached. Not stripped: names that only point at credential files (`AWS_PROFILE`, `KUBECONFIG`), other URL variables that may embed credentials (`HTTP_PROXY`, `PIP_INDEX_URL`), and the files themselves.

#### Image generation and configuration edits (S3.3d)

Both rules apply to every non-interactive session: attached roots and their managed descendants, pending sessions and closed ones. Interactive sessions are never affected. They come from read-only inspection of the OpenCode 2.2.6 binary and are tested with the recorded `permission.evaluate` key set and a fake context. On OpenCode, config-path writes were observed denied on 9 November 2026 ([live report](../docs/smart-routing-qualification.md#live-probe-run-descendants-and-s33d-harness-85ae5f4)); image generation was not observed.

- **Image generation.** `experimental_image_generate` is a direct model-visible tool (not a Code Mode one) that calls a paid image model in a background job and never passes through `model.request`. Before it starts, OpenCode asks permission with action `experimental_image_generate` (the tool ID) and the `provider/model#variant` it will call as the resource, then `edit` for an output `path` when one is given. The shim denies that action and also throws `image_generation_denied` from `tool.execute.before` for that tool.
- **Configuration edits.** Write, edit and patch (including a patch's move targets) all ask permission with action `edit` (the binary has no `write` or `patch` action; those names are denied the same way in case a later version uses them). Each resource is a path relative to the instance directory with `/` separators (`..` first when the file is above it inside the project, `.` for the directory itself), or an absolute path for a file outside the project. That directory is the plugin's `ctx.location.directory`: in the binary both the plugin context and `FileAccess` take it from the same location service. The shim resolves a relative resource against it. An edit is denied when any of its resources is a config path, when its resources are missing, empty, not a list or more than 256 (so a patch touching more than 256 files is denied), or when one cannot be read (not a string, empty, over 4096 characters, a control character, or a segment of only dots and spaces). A config path is one where, after the normalization below, in its raw segments or after resolving `..`:
  - any segment is `.opencode`, `.claude`, `.agents`, `opencode.json` or `opencode.jsonc`. Config discovery reads these at the instance directory and every ancestor, matching names case-insensitively, and loads agents, commands, modes and plugins from `.opencode`; `.claude` and `.agents` feed skills, and `.claude/settings*.json` may configure the Claude Agent harness (unverified). They stay fully denied;
  - `.config` is followed by `opencode` (the global config directory, also for a project in a home directory);
  - the absolute path is, or is under, a global or system config directory: `/etc/opencode`, `/Library/Application Support/opencode`, `$ProgramData/opencode` (default `C:\ProgramData`), `<home>/.config/opencode`, `$XDG_CONFIG_HOME/opencode` and `$OPENCODE_CONFIG_DIR`, computed from the server's environment when the plugin loads (values that are not absolute paths are skipped). Other absolute paths through a folder named `opencode`, `agent(s)`, `command(s)` or `mode(s)` stay allowed;
  - only when the instance directory is unknown (missing, not absolute or unreadable): a relative path whose first segment after any leading `..` is `agent`, `agents`, `command`, `commands`, `mode` or `modes`. OpenCode loads `{agent,agents}/**/*.md`, `{command,commands}/**/*.md` and `{mode,modes}/*.md` only inside config directories (system, global, `.opencode`, `.claude`, `.agents`), never from a project root or its ancestors. With the directory known, an instance inside a config directory is covered by the rules above, and `agents/planner.py` in an ordinary project is allowed; without it the shim cannot tell, so it fails closed;
  - a `protected_paths` entry matches as consecutive segments anywhere.

  Normalization: Unicode NFKC (so full-width lookalikes match; other scripts' lookalikes such as Cyrillic `о` are different names to OpenCode too), lower case (conservative also on case-sensitive filesystems), `\` as a separator, empty and `.` segments dropped, and each segment compared by its name before any `:` (NTFS streams, drive letters) with trailing dots and spaces ignored. Only these exact names count: `src/commands/x.ts`, `agents/planner.py` (directory known), `agent.md`, `commands.txt`, `opencode.json.bak`, `my-opencode.json`, `src/opencode/x.ts` and `/Users/x/dev/opencode/README.md` stay allowed. The shared table is `tests/opencode_plugin/config_paths.json`. Reading config is not affected.
- **`protected_paths`** (plugin option): up to 32 extra paths of at most 256 characters and 16 segments, normalized the same way, each matching as consecutive segments anywhere in a resource. They only add to the built-in set. An invalid option (not a list, an empty, unreadable or `..` entry, too many entries or segments) is detected when the plugin loads: `routing.health` answers `{state: "not_ready", reason: "protected_paths_invalid"}` without asking the routing child, so a launcher does not dispatch, and every managed edit is still denied (fails closed). The caps keep the hook fast: the largest option and a 256-file patch of 2048-segment paths are checked well within 500 ms (tested).
- `routing.health` answers `managed_denies: ["config_edit", "image_generation"]` with `ok`; `probe` takes the matching `worker_tools` states (see [What can be enforced](#what-can-be-enforced)).

A launcher must never invoke a project command (TUI or `session.command`) inside a managed session: a command's `` !`cmd` `` template runs through OpenCode's process runner, not the `shell` tool, so the `shell` permission and `shell.create.before` stripping do not apply to it (observed 9 November 2026), and a command can name its own agent and model. A model in a managed session cannot write or edit a command, agent, mode, plugin or config file while the shim is loaded. Residuals: user-invoked commands are not protected: their `` !`cmd` `` shells keep credential-like variables even while a session is attached, and only this launcher rule (never run project commands inside a managed session) keeps credentials away from managed work; an interactive session, a plugin that failed to load, and a session in an instance the launcher did not attach can still edit config; so can an advisory profile that allows `shell`, which reaches any path; whether the launcher's policy wins over an edited project config (edited before the attempt, or by an unmanaged session) is unverified; a symlink that already points into a config directory under another name is not resolved (the shim sees only the path OpenCode reports, and with `shell` denied a model cannot create symlinks); Windows short names (`OPENCO~1`) are not recognized; files that change instructions without changing permissions (`AGENTS.md`, `CLAUDE.md`, configured `instructions`) are not covered.

**Required live probe before cutover** (run 9 November 2026, [live report](../docs/smart-routing-qualification.md#live-probe-run-descendants-and-s33d-harness-85ae5f4)): on an attached root, (1) a prompt asking for an image: the permission is denied, no image job starts and no `model.request` fires for it; (2) a model `write` to `.opencode/command/x.md` and an `edit` of `opencode.json`: denied, files unchanged; (3) with a user-created command whose template is `` !`env` ``, run once under an attached root in an isolated server with a dummy credential in its environment, record whether the credential-like name is stripped (it may not be).

Results:
- **(2) partly observed.** Model `write`s that created `.opencode/command/x.md` and `sub/opencode.json` were denied, and the files stayed absent. An `edit` of an existing `opencode.json` was not attempted.
- **(3) observed: not stripped.** The command template's shell never reached `shell.create.before`.
- **(1) unobserved:** there was no image model.

Observed live: config-path writes denied for those 2 paths, with relative resources. Not observed live: an edit of an existing config file, image generation, absolute-path edits, and whether the launcher's policy wins over an edited project config. Those remain package-tested only.

A managed session passes only when the answer is `allow` with `authority: "verified"` for its attempt (otherwise `authority_unverified`). Everything else blocks the request before it is sent: a `blocked` answer, `unmanaged`, a timeout, an unreadable line, an answer with an unknown ID or another version, a missing state, the child exiting, an undeterminable chain with the evidence above, or a request over 4 KiB.

### Routing child

The shim starts one `python3 -I -B scripts/routing.py --serve` child per plugin instance on first use, with the `--settings` and `--ledger` pins from the plugin options and an environment without credential names. Requests are JSON lines `{"v": 1, "op", "id", ...}` and answers are matched by ID, so concurrent hooks share the child. Each request has about 500 ms, plus a one-time start-up allowance of 1 s after a spawn. On a stall, exit, unreadable line or unknown ID, the shim kills the child, starts a new one and retries once; if that also fails, the hook throws `routing_unavailable`. Killing the child fails every request waiting on it, and each of those is retried once on the new child, so one stalled request can delay the others by one timeout. After two such failures in a row the shim fails fast for about 1 s before starting a child again; it never gives up for good.

When the plugin shuts down, the child is killed, requests in flight fail, and no child is started again.

Plugin options: `python` (interpreter, default `python3`), `settings`, `ledger`, `timeout_ms` (at most 5000) and `protected_paths` ([S3.3d](#image-generation-and-configuration-edits-s33d)).

### Plugin RPC

The plugin registers RPC `routing` (`POST /api/rpc/routing/<method>` with `{"input": {...}}` and the `x-opencode-directory` header):

- `health` `{}`: asks the child for `status` within the request budget. Returns `{state: "ok", child: "up" | "respawned", version: 1, respawn_ms, managed_denies}` only when the settings are readable and the ledger exists and opens; `{state: "not_ready", reason: "settings_unavailable" | "ledger_absent" | "ledger_unavailable", version: 1}` when the child answers but cannot yet answer a check; and an error when the child does not answer (observed HTTP 500 with the child down; HTTP 400 `rpc.unavailable` when the plugin did not load). A launcher sends only after `ok` (see [Handshake](#handshake)).
- `attach` `{session_id, attempt_id, authority, funding_pool, model, deny_actions?}`: `session_id` must be a derived-shape ID and `model` is the dispatched route as `provider/model#variant`. A malformed or missing field, including any other session ID, is `invalid_attach` and reaches no child. Otherwise the shim, before recording anything:
  1. sends the child a strict `check` with the attempt, the session, the token and that route (kind `primary`, the given pool), and accepts only `allow` with `authority: "verified"` for that attempt (another attempt's session is `session_mismatch` there);
  2. asks the child about the session alone and accepts only `authority_required`, so the ledger already owns it as a dispatched hold's session. With step 1 that makes it the attempt's own derived session; the command returns no owner field, so ownership is inferred this way;
  3. then applies its local limits: a session managed under another attempt, and more than 256 attached sessions (children are not counted; an attachment that is never detached keeps its place).

  Every refusal after the shape check is the same `attach_refused`, whatever the reason (wrong token, unknown or closed attempt, unsent admission, another attempt's session, a session the ledger does not own, the limits, an unavailable child), so a caller without the token learns nothing about the ledger or this instance. The same attempt may attach again; that keeps the stricter rules, because `deny_actions` only grow. Returns `{state: "attached", session_id}`.
- `detach` `{session_id, attempt_id, authority}`: only for an attached root with the same attempt and token (always compared, in constant time, also when nothing is attached); everything else, including a descendant, an unattached session and a repeated detach, is `detach_refused`, and a malformed field is `invalid_detach`. Returns `{state: "detached", session_id}` and releases the session and the children found through it.
- `descendants` `{session_id, attempt_id, authority}`: the shim's own record of the root's managed descendants, so the launcher does not have to trust its own session listing ([S3.3c](#usage-accounting-and-resync)). The same authority rules as `detach`: only an attached root with the same attempt and token, compared in constant time; everything else (a wrong or other attempt's token, a descendant, an unattached, never-attached or already detached root, a repeated call after detach) is `descendants_refused`, and a malformed field is `invalid_descendants`. It asks the routing child nothing and changes nothing. Returns:

  ```json
  {"state": "ok", "root": "<session_id>",
   "descendants": [{"session_id": "ses_…", "parent_session_id": "ses_… | null"}],
   "truncated": false, "complete": true, "reason": null,
   "cache": {"recorded": 3, "retired": 0}}
  ```

  - `descendants`: every session recorded as a managed descendant of that root, at any depth and however it was learned (creation event, lookup, a pending child at attach), including those recorded before an earlier detach of the same root (`cache.retired`), sorted by ID. Only IDs and parent links; never titles, messages or prompts, and never another root's sessions. `parent_session_id` is the direct parent the shim knew when it recorded the session, or `null` when it did not (for example a pending child whose cached link was evicted).
  - At most 512 entries; beyond that `truncated` is `true`.
  - `complete` is `true` only when the shim can vouch that no descendant is missing. Otherwise `reason` is the first that applies: `event_stream_unavailable` (the host has no creation-event stream, or it ended or failed), `root_creation_unobserved` (the root's own first `session.created` was not seen while it was attached: it was created before `attach`, or attached again after a detach or a plugin restart; a repeated creation event never vouches again, because the shim remembers the last 4096 derived-shape creations it saw), `descendant_limit` (the root's budget was exceeded, so a descendant may be unrecorded), `lineage_lookup_failed` (while it was attached, a model request or subagent spawn came from a session whose parent chain could not be determined: a `session.get` lookup failed or was still remembered as failed, or the walk reached its 8-lookup or 64-session limit; that session may belong to any attached root. `permission.evaluate` and other hooks that cannot spend never mark it) or `response_truncated`.

  A child the shim found only through a lookup counts as recorded, and `complete` can stay `true`: for money that is sound, because every model request goes through `model.request`, which either records the session under its root or, when its chain is undetermined, marks the root incomplete.

  As with every RPC, a refusal reaches the caller as HTTP 500 with no reason code; the launcher then has no answer and passes `None` (see below).

  **Required live observation before API-funded qualification** (observed 9 November 2026 by the qualification harness's `descendants` stage: both runs as expected, with a tool subagent, a command child and an API child; see the [live report](../docs/smart-routing-qualification.md#live-probe-run-descendants-and-s33d-harness-85ae5f4)):
  1. Positive run: `health`, `dispatch`, `attach`, create the derived root, then send a prompt that spawns both a tool subagent and a `subagent: true` command child. Wait until every session is idle and call `descendants`. Expect `complete: true`, both children with their parents, and a set equal to the launcher's own listing. Then `record complete` and `detach`; a further `descendants` must be refused.
  2. Negative run: create the session before `attach`; `descendants` must answer `complete: false` with `root_creation_unobserved`.

So a client of the server without the token, such as an interactive agent or a worker that reaches the server through a shell, can neither attach an interactive session nor detach a managed one, and a token holder can attach only its own attempt's derived session.

### The `unmanaged` answer

`{"v": 1, "state": "unmanaged"}` is the S3.4 answer for a `check` with only a `session_id` the ledger does not know. The shim sends such a check only to ask about a derived-shape session ID (see [Managed and interactive sessions](#managed-and-interactive-sessions)). The command validates a `request` before it resolves the session, so the question carries fixed placeholder facts (provider `opencode`, kind `primary`) that are never used. For an attached session `unmanaged` contradicts the launcher and blocks (`unexpected_unmanaged`).

### Residual risks

- A plugin instance that restarts or reloads during an attempt forgets its attachments; until the launcher attaches again, that session runs unguarded.
- A managed child that was not recorded as a managed descendant passes as interactive when its `session.get` lookup fails (or returns anything but that session), and also when its chain to the root is longer than 64 sessions. It goes unrecorded when its creation event was missed, when its first request arrives before its creation event, when the event stream has stopped (lineage then relies on lookups for the life of the instance), or when it falls beyond both the descendant budget and the over-limit record.
- A session created through the server API without a parent and with an ID that is not derived (or derived but unknown to the ledger) is a root and interactive, so a worker that can reach the API (for example through a shell) can still run unmanaged sessions that way; it cannot spend an attempt's admission, because that needs the token. Only profiles that deny shell, Code Mode `execute` and `webfetch` keep workers away from the API.
- A derived session the ledger knows passes as interactive while the ledger cannot answer (absent, busy, a child failure or a timeout), until the shim asks again after 5 s, or while 8 hook questions are already in flight. A burst of derived-looking creations does not let one through, but it can delay learning about a session until its first hook asks.
- Sessions of a finished attempt pass as interactive when their record is gone: the attempt aged out of the ledger, or the session was forgotten (more than 4096 sessions kept past detach, or the lineage cache evicted it and it was never recorded under an attached root). A child created through the API under a pending session is blocked only if its creation event was seen (with no root attached, the shim makes no lookups).
- A token holder can attach only its own attempt's derived session. Ownership is inferred from two command answers (step 2 above), not from an owner field.
- The token is in the plugin's memory and in the `routing.attach` request body, so other code in the server process, or anything that can read the server's requests, could see it; whether OpenCode logs RPC input has not been observed.
- A managed session in an instance the launcher did not attach (another directory spelling, another server) is unguarded.
- `routing.descendants` vouches for its set only as far as the creation-event stream delivers every `session.created` while the root is attached; that delivery is assumed, not observed. A `complete` answer can still miss a child the stream never delivered and nobody looked up, a session created through the API without a parent (a root of its own, so not this attempt's descendant), and a child created between the launcher's re-read and its `descendants` call (the launcher reads only once the sessions are idle). The shim detects only an event stream that ends or throws, not a silent gap in delivery. A model request or spawn from any session whose chain is undetermined makes every attached root's answer incomplete for the rest of its attachment, so an interactive session whose lookup fails (or a client that builds a chain deeper than 64 sessions and sends one request on it) turns API-funded attempts in that instance to `cost_unknown`. This errs toward an unknown cost, never a low one, and is accepted before the canary; replacing the sticky flag with a bounded, decaying per-root set is a planned follow-up. After 4096 later derived-shape creations a root's first creation is forgotten, and a repeated event for it could vouch again.
- Commands run inside an allowed shell, and a plugin that failed to load, stay unenforceable (capability matrix).
- `websearch` is a model-reachable tool that sends query text to a third-party search provider, an exfiltration channel like `webfetch`, and the shim does not tighten it (a planned follow-up; a worker profile can deny it).

## Usage accounting and resync

[`runtime/opencode_accounting.py`](../runtime/opencode_accounting.py) turns a re-read OpenCode attempt into the usage report the routing command's `record` takes. Like the adapter, it is pure, and it reads only the adapter's normalized messages and events. Errors are `AccountingError` with a fixed reason that never repeats the payload.

- **Source of record.** Usage comes from stored message tokens and the session's token total. `session.usage.updated` is volatile and never replayed, so it is never used. Step events carry the same tokens but are not counted either.
- **`usage_from_messages(messages, session_total, session_id=…, funding=…, complete=…, session_cost=…, children=…, lineage=…, shim_descendants=…)`** accounts one attempt.
  - Each assistant message is a `primary` request and each compaction message a `compaction` request, with the message ID as `receipt`, in creation order.
  - Above 32 requests (one report's limit) they are grouped by kind, model and variant, without receipts. Above 32 routes they are grouped by kind with model `unknown`, every cost `null` and the reason `too_many_routes`.
  - The result's `usage` is the S3.6a `{source, requests}` object, or `null` when nothing was requested. The result also has `totals`, the root's `title`, per-session `sessions`, `message_ids`, `unknown` reasons, `reported_cost` and the latest `rate_limit` observation.
  - Identical duplicate messages count once; a message ID with different content is refused.
  - Normalized messages carry no session ID, so a message belongs to the session state that lists it. The same message under two sessions is refused.
- **Child sessions.** A parent's token total excludes its subagent sessions (the probes show this), so the attempt's spend includes them only when the caller passes them as `children`, each as `normalize_session` output plus its messages.
  - A child links to its parent in two ways, at any depth: a subagent call's `child_session_id` in an included session, or the child's own `parent_session_id` (the `parentID` from `session.get`). A `subagent: true` command creates its child directly, with no subagent call in the parent, so `parentID` is its only link (live re-qualification, 9 November 2026).
  - These make every cost unknown:
    - a spawned session that is not included (`child_session_unaccounted`);
    - a subagent call with no child session, for example one that errored, was aborted or is still starting (also `child_session_unaccounted`), because it may have spent before losing its link;
    - tool calls the adapter dropped (`tool_calls_dropped`).
  - Every included session must be reachable from the root through these links. An unreachable session (including an island of sessions spawning or parenting each other), a cycle, a link back to the root, a `parent_session_id` outside the attempt or contradicting a subagent call's link, and a root whose parent is in the attempt are all refused. A child that two sessions reference counts once.
  - **Lineage.** `lineage` is the launcher's list of `{session_id, parent_session_id}` for every session it knows of under the root, from session listing and lineage events. Command children count like any other descendant. Any listed session whose recorded parent chain reaches an included session, but that is not itself included, adds `child_session_unaccounted`; sessions whose chain leaves the list are ignored. A listed session with two parents, a parent that contradicts an included session's link, or a cycle is refused (`invalid lineage`); more than 1024 entries is `too many sessions`. Launchers must supply `lineage`: without it the result carries `lineage_not_checked`, which makes an API route's cost unknown (the hold ends `cost_unknown`) rather than silently complete, and is only a flag on subscription routes.
  - **Shim cross-check (S3.3c).** On its own, `lineage` trusts the launcher: a child left out of both `children` and `lineage`, or lineage that lies about a parent, settles complete with that child's spend uncounted. So launchers also pass `shim_descendants`, the plugin's [`routing.descendants`](#plugin-rpc) answer for the root, or `None` when the call failed. `cross_check_lineage(lineage, shim_descendants, root, children=…)` is the pure helper behind it:
    - every shim entry with a known parent that the listing lacks is added to `lineage`, so its chain is checked like the launcher's own entries;
    - every shim-recorded descendant must be included in `children`: one that is not adds `child_session_unaccounted`, whatever the listing says about it or its parent (a `null` shim parent cannot contradict a false listed parent, so only inclusion proves its spend was counted); a launcher-listed session the shim did not record is fine;
    - a shim parent that differs from the listed parent (including a listed `null`) or from an included child's verified parent, the root among the descendants, a self-parent or one session with two parents is refused (`invalid lineage`); a malformed answer is `invalid shim lineage`, an answer for another root `session mismatch`, more than 1024 entries `too many sessions`;
    - `complete: false` or `truncated: true` adds `shim_lineage_incomplete`, and `None` adds `shim_lineage_not_checked`.
    These flags make every API cost `null` (the hold ends `cost_unknown`) and are only flags on subscription routes. The shim set never stands in for the launcher's listing: `lineage: None` still adds `lineage_not_checked`. Omitting `shim_descendants` keeps the launcher-trusting behaviour; API-funded managed attempts are qualified only when the launcher passes it and that path has been observed live (not yet). `reconcile_with_state` takes it as the state's `shim_descendants` key.
  - Each child's tokens, title remainder and unknowns count like the root's.
- **Finished messages.** A message is finished when it has a completion time or a finish reason, or when an idle message was created after it. The recorded compaction message has neither of its own, and the idle message after it is the only sign that it ended. An unfinished message is still counted with its current tokens, but its session's title is unknown and every cost becomes `null` (`message_in_progress`).
- **Title tokens by subtraction.** A title request creates no message, so its tokens are the session total minus the sum of its messages, per token class (`title_tokens`).
  - The result is unknown when:
    - any class would go negative;
    - the message list may be incomplete (`complete: false` for a paging gap);
    - a message's tokens are missing, or a message has not finished;
    - an unknown record, or tokens on a non-model message, appear. The adapter returns a `synthetic` message (how a command child's result reaches its parent; only its type was recorded) as `kind: "synthetic"` only when it has no model, no non-zero cost and no tool parts, otherwise as unknown, so a child link on it is never lost silently. A `synthetic` record is never a request and never an unknown record, but tokens on it count as unexpected;
    - the session total lacks a class.
  - A non-zero remainder becomes one `title` request with model `unknown`.
  - Whether `generate` requests also create no message is unverified. If they do, their tokens are in this remainder too.
- **Cost.** Units stay separate: tokens, USD micro-units and quota fractions are never added. Cost is never derived from tokens.
  - With `funding: "subscription"` the source is `host_message_totals` and every `cost_usd_micros` is `null`. OpenCode's figure appears only in `reported_cost` (`basis: "provider_estimate"`): a provider's token-price estimate is not proof of out-of-pocket spend.
  - With `funding: "api"` the source is `estimate`. OpenCode computes cost locally from a price catalog and reports 0 for unpriced or custom models, so its figure is not a receipt. S3.6a charges an estimate at no less than the admitted estimate and releases at most the padding.
  - On API routes each message's cost becomes micro-units, rounded up. The title's cost is the session cost minus the messages' costs.
  - A zero or missing cost for a request that used tokens is unknown. So is a missing or non-positive cost difference for a title with tokens, and so is any unknown above.
  - When any cost is unknown, every cost is `null`, so the hold stays `cost_unknown` and is never released on a zero.
  - A message with no tokens and cost 0 stays 0.
- **Event gaps.** `track_events(events, state)` checks `durable.seq` per aggregate and returns `resync_needed` with the aggregate, the last in-order sequence number and the reason. The reasons are `gap`, `out_of_order`, `seq_conflict` (same number, another event), `reset` (0 again), `version_changed` and `joined_late` (first seen after 0). An exact duplicate is only counted, and volatile events are ignored. The input state is never changed.
- **Resync.** After a gap, and always at attempt end, the launcher re-reads the sessions and their messages and calls `reconcile_with_state(previous, {session_id, messages, tokens, cost?, complete?, children?, lineage?}, funding=…, tracker=…)`.
  - Totals are recomputed from the state, never accumulated, so repeating a resync changes nothing.
  - The result reports token deltas, added and missing messages, and `regressed` classes (a deleted or reverted message). These are reported, never charged back; acting on them belongs to S3.6b-2.
  - With `tracker`, it also re-baselines every included session (`mark_resynced`).
- **Rate limits.** `rate_limit_observation(record)` passes Claude Agent `native.rateLimit` through as an observation with explicit units: 0–1 fractions, resets in epoch seconds, and the observation time (completion, else creation) in epoch milliseconds. Windows the adapter could not read, such as a percentage, are listed as unknown. A utilization above 1, or a reset that looks like milliseconds, is refused. Window headroom comes from this telemetry, never from token arithmetic.
- **`normalize_session(session)`** reads a `session.get` record into `{session_id, parent_session_id, tokens, cost}`. It validates the totals with the adapter's message normalizer, because the adapter has no session normalizer.
- **`consistency_report(session_state)`** returns bounded diagnostics: message counts by type, duplicates, conflicts, unknown records, missing tokens or models, unfinished messages, spawned, included and unaccounted child sessions, listed descendants that are not included and lineage conflicts and loops (`lineage_unaccounted`, `lineage_conflicts`, `lineage_loops`, each `null` without `lineage`), subagent calls without a child session, dropped tool calls, and whether the title remainder is known. It counts problems instead of raising, and carries IDs, counts and field names only.

**Wiring.** The [managed launcher](#managed-launcher) follows these steps.
1. The launcher waits until the attempt's sessions are idle: the root's run has ended and no subagent is still running.
2. It re-reads the root session with `session.get`, then every page of its messages, then every descendant session the same way, including command children found only through `parentID`.
3. It normalizes these with the adapter and `normalize_session`.
4. While the root is still attached, it calls `routing.descendants` for the root with the attempt's token.
5. It calls `usage_from_messages` with the hold's funding, the descendants as `children`, every session it knows of under the root as `lineage` and the `descendants` answer (or `None` if the call failed) as `shim_descendants`. A shim-recorded session it did not re-read is `child_session_unaccounted`; re-reading it and passing it in `children` clears that.
6. It sends `result["usage"]` in `record complete {usage}`, then calls `routing.detach`.

It sets `complete: false` for any session whose paging was not exhaustive. Re-reading before the sessions are idle gives an unknown cost rather than a low one. A launcher may also feed `/api/event` records to `track_events` and resync when one is flagged; the managed launcher does not read the event stream and relies on the re-read at attempt end. This assumes one root session per attempt; a session reused across attempts would need the previous accounting as a baseline.

Observed in the live re-qualification (9 November 2026), for launchers:
- A `subagent: true` command does not pass through `tool.execute.before`, so the shim's spawn checks never see it. The shim stopped the child at its first model request through the parent lineage it learned from `session.created`. The blocked child's failure still started an extra parent turn on the attempt's route, which costs the parent.
- RPC refusals such as `attach_refused` reach the caller as HTTP 500 `rpc.internal` ("RPC call failed") with no reason code, so a launcher cannot tell a refusal from a routing-child failure and must treat both as "do not send".

### Uncertain subscription holds (S3.6c)

When the launcher cannot confirm a launch it records `uncertain`. The hold then keeps its window claim and its concurrency place, and a client's `complete` stays `reconciliation_required`. `reconcile_uncertain` settles only dollar holds. For a subscription hold, the operator uses `reconcile_subscription{attempt_id, evidence, event_id}` ([`runtime/subscription_reconcile.py`](../runtime/subscription_reconcile.py)). Package-only: it is not observed on OpenCode.

- **Scope.** The op applies only to an open `uncertain` hold whose claims are all `win:` window claims, with no organization and no dollars. Any other hold is `hold_state_forbidden`, including admitted, dispatched, `cost_unknown` and uncertain dollar holds. A closed hold is `attempt_closed` and an unknown one `unknown_attempt`. The op never charges dollars and never changes a derived block reason.
- **Operator op rules.** These rules apply to every operator op: `resolve_cost_unknown`, `resolve_overrun`, `reconcile_uncertain`, `resolve_block`, `reconcile_subscription`, `drop_debit`, `settle_legacy_call` and `seed_window`. Each runs only as a one-shot `scripts/routing.py <op>` command, the only service whose `one_shot` flag `main()` sets. The `--serve` child and every in-process service, a launcher's `managed_service` included, answer `operator_op_not_served` before reading anything. `record` can never reach an operator op (`record_unsupported`, or `invalid_request` for its fields). Each op is idempotent by `event_id` in the S3.6a event table:
  - the same payload returns the original outcome with `duplicate: true` and writes nothing;
  - another payload under the same id is `event_conflict`;
  - refusals are not remembered;
  - 15 racing processes apply one effect;
  - the event table is bounded, so an old row can be pruned. A replay after that is no longer a `duplicate`: it meets the state the op left behind. Replaying `settle_legacy_call` then gets `call_closed`, or `block_not_pending` if it left an over-bound call. Replaying `drop_debit` gets `debit_not_pending`, or `marker_stale` if the key was debited again. Neither applies twice. Replaying `seed_window` meets its own bounds again: `fresh_observation_exists` once a host has reported the window, or `invalid_request` once its `reset_at` has passed; otherwise it writes the same seed again.

  The audit is the event row: ids, labels and integer totals only, never receipts, session ids, tokens or content.
- **`evidence{kind: host_usage, session_id, usage}`.** After stopping the worker, the launcher re-reads the attempt's sessions once they are idle, as in steps 1–5 of the wiring above, and sends `usage_from_messages(...)["usage"]` with source `host_message_totals`.
  - The hold must have been dispatched through `dispatch` (else `dispatch_required`), and `session_id` must be its derived session (else `evidence_mismatch`). Another usage source is `evidence_invalid`.
  - It settles exactly like a subscription `complete`: the window claim and the concurrency place are released, the units are recorded as an observation and the root aggregate is updated. The settlement adds `resolution{basis: host_usage}`.
  - A message or session the host no longer returns proves nothing (a not-found answer can also mean deleted, reverted, or another server or directory), so an empty re-read cannot be sent as `host_usage`. The operator uses `abandon` instead.
- **`evidence{kind: abandon}`.** The operator stops the worker first and accepts the worst case: the request may have been sent and may have used window units.
  - The concurrency place is released at once. The hold's window claims become a window debit per window key in the ledger record (`window_debits`: units added up and the latest abandon time kept per key, at most 32 keys). Admission keeps counting the debit against that window's headroom.
  - No units are invented or observed: the root aggregate gets none.
  - When the table is full, an abandon that adds a key is `ledger_capacity_reached`, and the hold stays uncertain.
  - Outcome: `abandoned` with `settlement{kind: window, released: {}, debited, observed_units: null, resolution{basis: abandon}}`.
- **When a debit clears.** A debit clears only when a validated `prepare` snapshot carries a qualifying observation of the same pool and window. A qualifying window:
  - is the only window with that id in the snapshot, and is explicitly fixed (`rolling: false` exactly; a missing `rolling`, `null` or `0` never qualifies, although admission still treats a missing key as fixed);
  - is `fresh` with known `used`, a numeric `reset_at` and a positive `length`;
  - is current (`reset_at` after the snapshot's `now`);
  - began (`reset_at − length`) no later than `now` and at least 60 s (the command's clock drift bound) after the abandon.

  The abandoned request's units cannot be in such a window. Only two kinds of `prepare` clear a debit: the one-shot command, or an in-process service whose snapshot the collector built for a managed project. The shim's persistent `--serve` child, which a plugin or worker can reach, never clears one. Neither does an in-process service given the caller's own snapshot. Admissions there still count the debit. The debit is removed once, in the admission transaction, whatever the admission outcome, with an audit row `window_debit_cleared`. The row's id is longer than any client `event_id` may be and unique per clearing, and it is inserted without replacement, so it never overwrites a client event or an earlier audit row.

  The admission transaction is a growing write. When the ledger record is above its soft limit (`SOFT_RECORD`), `prepare` commits nothing, so a debit never clears through `prepare` then: it fails closed and stays counted until the record shrinks.

  A newer `now`, `epoch_at` or `snapshot_id` alone never clears a debit: neither does the same window seen later, a rolling window, a window with no reset or length, or one that has not begun or has already reset. A `used` figure cannot show that it already includes the abandoned units, so usage numbers never clear a debit. Nothing is released on lease expiry or time alone.
- **`drop_debit{key, marker, event_id}`.** A debit that never clears on its own, such as a rolling window's, would otherwise keep its place in the 32-key table for good. The operator removes one with this one-shot op ([`runtime/subscription_reconcile.py`](../runtime/subscription_reconcile.py)), after reviewing the window. Package-only: it is not observed on OpenCode.
  - `marker` is the `dd_` value `status` lists for that key. It is a digest of the ledger identity, the key, and the debit's units and mark, so a debit that grew or moved since the review makes it `marker_stale`. A key with no debit is `debit_not_pending`, and any other shape `invalid_request`.
  - It removes only that debit, which releases its window headroom. It never changes a hold, a dollar figure or a block reason.
  - It follows the operator op rules above. The audit row `drop_debit` holds the key and its units only.
- **`seed_window{pool, window, used, limit, reset_at, length, event_id}`** (C.3 design 7.1, user decision 6). The collector learns a subscription window only from a settled attempt, so the first managed launch on a route finds none (`window_unobserved`) and `prepare` stays `pending`. The operator seeds that window once with this one-shot op ([`runtime/routing_observations.py`](../runtime/routing_observations.py)), from a reading taken by hand, in the host's own unit, scale and length. Package-only: it is not observed on OpenCode.
  - Only a subscription window: a `qualified` `included_subscription` route of the manifest names it in its `demand`, and no dollar route of any status draws on the pool. A dollar pool, an unknown pool or window, and a window stored with an `organization` are `invalid_request`.
  - Bounds: `used`, `limit` and `length` are non-negative integers (never bools or floats) with `used <= limit`, `limit > 0` and `length > 0`. `limit` is exactly 1000, the full scale of `utilization_thousandths` the host stores every window with (`opencode_launcher.WINDOW_UNITS`), because a larger limit would multiply the headroom. `length` is exactly the host's length for that window id (`opencode_launcher.RATE_WINDOWS`: `5h` 18,000 s, `7d` 604,800 s); which window ids a pool has comes from the manifest route's `demand`, since plans differ (one may have no `5h` window). A window id the host never stores cannot be seeded. `reset_at` is an integer after the command's clock and no later than that clock plus `length`. Anything else is `invalid_request`. An unusable manifest is `route_manifest_invalid`, and an unsafe or malformed window store its `observation_store_*` reason.
  - It is refused (`fresh_observation_exists`) while a host observation of that window is no older than 900 s, or dated ahead of the clock. It replaces a stale host observation or an earlier seed.
  - The seed is stored in the private window store with `unit: utilization_thousandths` (`WINDOW_UNIT`), `rolling: false`, `observed_at` from the command's clock and `source: operator`, so the collector accepts it and keeps it fresh for the usual 900 s. Admission sees only the window, never its source.
  - The first host observation the launcher stores (`store_window`) replaces a seed whatever its time; a seed never replaces a fresh host observation. The host path can never write a `source`, and a stored window whose `source` is not `operator` is not a window.
  - It follows the operator op rules above. The audit row `seed_window` holds the pool and window labels and the seed's integers only.
  - `status` lists the stored windows as `windows{state, windows: [{pool, window, source, observed_at, fresh}], more}` (16 at most): `source` is `operator` while the seed is in use and `host` once a host observation has replaced it. An unreadable store is `windows{state: unavailable, reason}` and never fails `status`.
- **Status.** `ledger.reconcile.reconcile_subscription{count, ids, more}` lists the uncertain subscription holds, `ledger.reconcile.window_debits{count, keys, more}` the debited window keys, and `ledger.reconcile.drop_debit{debits: [{key, units, at, marker}], more}` each debit with its `drop_debit` marker (16 per list). While such a hold is open, `reconcile_hint` carries a fixed subscription text, appended to the dollar text when both apply. A debit alone needs no operator action and leaves the hint `null`.
- **Trust.** The prepare snapshot is the collector's, the same input admission already trusts for headroom, so a forged snapshot that can admit work can also clear a debit. Evidence and abandons are the operator's word: offline, nothing can check a host re-read. A request still in flight when the hold closes is covered only by the debit (abandon) or by the re-read (host_usage).
- **Capacity.** The debit table adds 18,226 characters to the worst-case ledger record: 10,716,910 of 12,000,000 (89.31%), against the 90% test ceiling. `drop_debit` and the state version add no field, so the figure is unchanged.
- **Downgrade.** The ledger is at state version 5 ([`runtime/ledger_versions.py`](../runtime/ledger_versions.py)), so code from before the debits refuses it with `ledger_identity_changed` instead of ignoring them. The 4→5 step changes no run, hold, handoff or debit, and is written with the ledger's next write.

## Managed launcher

[`runtime/opencode_launcher.py`](../runtime/opencode_launcher.py) runs one managed attempt on OpenCode (C.3 slice C3-3), and [`scripts/opencode_launch.py`](../scripts/opencode_launch.py) is its JSON command. It uses the host-neutral launcher core (`runtime/routing_launch.py`) and the routing service from `scripts.routing.managed_service`, so the project pin, the observations (built by the service's collector, never sent by the launcher) and the `seen` revisions passed through in the result all come from there. Package-tested only, with a fake server and the real routing command on temporary stores; it has not run on OpenCode.

The launch, in order. A refusal before `dispatch` sends nothing and closes any admitted hold with `not_dispatched`:

1. A checkout that is not a managed project answers `project_not_managed` and touches no host; the caller keeps its current path.
2. The `status` preflight of the core: `authority_required` on, `unstamped_open_holds: 0`, and the dollar items when the admission is a dollar route.
3. `routing.health` answers `ok` (anything else, including an RPC error, is `host_unhealthy`), and the adapter's `probe` rates the host `enforced` with the worker profile below and the `managed_denies` health lists (otherwise `profile_not_enforced`). Nothing is prepared yet.
4. `prepare`, then the core's check of the admitted route against the host's model listing (`GET /api/model`, every listed variant, in the shim's harness naming such as `claude-agent-sdk via opencode`) and against the [entitlement rule](#route-identity): `catalog_mismatch` or `route_not_entitled`.
5. Immediately before `dispatch`: an API-funded admission is refused with `api_funding_unqualified` until the required positive and negative [descendants runs](#plugin-rpc) have been observed with real costs (user decision 4), and `routing.health` is asked again.
6. `dispatch`, then `routing.attach` with the token and `deny_actions` (`external_directory`, `shell`, `bash`, `webfetch`, `websearch`). A refused attach is `attach_failed`: no session was created and no prompt sent, so the launcher closes the hold with `record complete` and no usage. If the attach call itself fails (a lost answer rather than a refusal), the shim may still have recorded the attachment, and the launcher never detaches it; nothing is spent, because no session was created, and the attempt is closed.
7. It creates the derived session, titled at creation (so OpenCode sends no title request) and with the worker profile as its permissions, then sends the prompt with the derived message ID. If the session cannot be confirmed, the prompt does not answer HTTP 200, or the attempt is not idle within 30 minutes, the launch is unconfirmed: the launcher records `uncertain`, answers `launch_unconfirmed` with the one-shot op that settles it (`scripts/routing.py reconcile_subscription`, or `reconcile_uncertain` for a dollar hold), detaches, and never dispatches again.
8. Once the root and its descendants are idle, the [wiring](#usage-accounting-and-resync) steps: re-read, `routing.descendants` (`None` when it fails), `usage_from_messages`, `record complete`, then `routing.detach`. The token is then forgotten.
9. For a subscription route, the latest Claude Agent `native.rateLimit` windows are stored for the collector: `five_hour` as window `5h` (18,000 s) and `seven_day` as `7d` (604,800 s), fixed, with a limit of 1,000. Each window declares its unit in the field `unit` as `utilization_thousandths` (a thousandth of the provider's utilization), so a manifest route's `demand` for these windows must use the same unit. The manifest declares it as `window_unit`, and the collector leaves a subscription route out when that declaration is missing (`window_unit_undeclared`) or a stored window's `unit` is missing or different (`window_unit_mismatch`).
10. When an assistant message of the primary session itself, on the admitted model and variant, carries an HTTP 400 with `model_not_found` in the upstream body, the attempt still settles normally, the result says `not_entitled: true`, and the launcher writes a `not_entitled` mark for that route and its manifest account; the collector leaves the route out until the user clears the mark. A child session's refusal, another model's, or a 400 without `model_not_found` is not a mark. When the account cannot be read from the manifest, no mark is written and the result says `entitlement_mark: account_unknown`. Nothing is retried on another route.
11. An interrupt (Ctrl-C, or SIGTERM or SIGHUP to the command, which it turns into an exception) never leaves a hold plainly open. After a confirmed `dispatch` the launcher records `uncertain`. Before that, including a `dispatch` that was refused or whose answer the interrupt cut off, it records `not_dispatched` with the core's event id; the ledger accepts that only while the hold is still `admitted`, because a dispatch commits atomically, and if it answers `hold_state_forbidden` the dispatch did commit, so the launcher records `uncertain` instead (any other doubt once a `dispatch` was sent is `uncertain` too). The first signal switches SIGTERM, SIGHUP and Ctrl-C off, so nothing interrupts the cleanup: the command still detaches, stops its server and answers `interrupted` (exit 1).

**Worker profile.** Session permission rules, where the last matching rule wins: deny everything, allow `read`, `glob`, `grep`, `list`, `edit`, `todoread` and `todowrite`, then deny `external_directory`, `shell`, `bash`, `webfetch`, `websearch`, `execute`, `subagent`, `task`, `skill` and image generation. MCP and every other tool fall under the first rule. `external_directory` covers edits outside the project; whether reads outside it are refused is unobserved.

**The server it starts.** The command starts one `opencode serve` per launch on a free loopback port, in the checkout's canonical directory, and stops its process group afterwards, also on an interrupt, which also stops the worker. The plugin wrapper and the server log (which may print the password) live in a private temporary directory that is removed on stop.

- **Environment: an allowlist**, as in the live-qualified harness. `HOME` (OpenCode and the Claude Agent provider find their sign-ins and data under it), `USER` (the macOS keychain lookup of a provider sign-in; the harness ran live with it), `LANG`, `TMPDIR`, and `XDG_DATA_HOME` (OpenCode keeps its data, including its `auth.json` sign-ins, under it when the user set it), each copied from the caller whenever it is set. `PATH` is fixed (`/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin`), never the caller's. Nothing else passes: no credential-like name, `NODE_OPTIONS`, `BUN_*`, `PYTHON*`, `LD_*`, `DYLD_*`, `XDG_CONFIG_HOME` or inherited `OPENCODE_*`. The launcher adds `OPENCODE_DISABLE_AUTOUPDATE`, `OPENCODE_DISABLE_MODELS_FETCH`, `OPENCODE_DISABLE_PROJECT_CONFIG`, a random in-memory `OPENCODE_SERVER_PASSWORD`, and the inline config below.
- **Inline config** (`OPENCODE_CONFIG_CONTENT`): the routing shim as the only plugin, pinned to the managed service's own settings and ledger with both store directories in `protected_paths`; `mcp: {}`, `formatter: false` and `lsp: false`, so no MCP server, formatter or LSP server (each can run project code); and the worker profile's rules as `permissions`.
- **Pre-canary requirement.** The launcher keeps the user's configuration directories so provider sign-ins work, so a project or global config may still load next to the inline one; the names and keys above may not be honoured. Before the canary, a live probe must show that a hostile project `opencode.json` or `.opencode/` and a hostile global config can add no plugin, MCP server, formatter or LSP server and cannot relax the permissions, and that a session's read of OpenCode's own `auth.json` is refused, or else record that read as an accepted risk. If the probe fails, the fallback is private configuration directories (`XDG_*`) holding a narrow copy of the provider sign-ins; that copy needs the user's approval and is not built.

**What it never does.** It never invokes a project command (TUI or the session command API) in a managed session, never runs an operator op or `set managed_projects`, never retries a route or a lost acknowledgment with a second `dispatch`, and never prints, logs or stores the token, the server password or the prompt. The token reaches only `routing.attach`, `routing.descendants` and `routing.detach`.

**Activation self-check.** `managed_self_check(workdir)` is the activation gate's "OpenCode launcher" capability: in a child process, against a fake server and the real routing command on stores inside `workdir`, an unhealthy host, an advisory profile, a catalog mismatch and a refused attach each stop before a session is created, one launch settles, and no token appears in any result.

**Not yet observed (live runs wait on the user).** Everything in the pre-canary requirement above; that OpenCode 2.2.6 honours `OPENCODE_CONFIG_CONTENT`, `OPENCODE_SERVER_PASSWORD` and `OPENCODE_DISABLE_PROJECT_CONFIG` (the names are in the binary; their effect is unobserved); that the fixed `PATH` reaches the provider tools the user's sign-in needs; that session permissions given at creation enforce the `external_directory` deny; reads outside the project; models listed without variants (effort `none`); and the window unit against real manifest demand (user decision 5).

## Evidence limits

Tests drive the adapter with the committed, sanitized probe fixtures in `tests/fixtures/smart-routing/probes/`. Most hook entries there are the probe plugin's summaries: their key sets and recorded values are real, while header, base URL and environment values were never recorded and are supplied by the tests. `s3-3-shim-live.json` holds full sanitized payloads recorded with this shim loaded, and what the shim blocked. The shim's own tests run under `node --test` with a fake routing child and with the real `routing.py --serve` on pinned temporary stores (prepare, dispatch, attach with the token, checks); the authority handshake was observed live once on OpenCode 2.2.6 with `claude-agent/haiku#low` ([live qualification](../docs/smart-routing-qualification.md): attach, allowed request, blocked unattached and wrong-token sessions, detach), while settlement, the closed-attempt block and the lost-acknowledgment drill were not reached. `routing.descendants` (S3.3c) is tested only with a fake event stream and the real `routing.py --serve`; it has not been called on OpenCode. Accounting rests on three recorded sessions with complete message lists: in one, the remainder after subtracting the messages is the title request (2 input, 9 output, 605 cache-read and 549 cache-write tokens); in the two with titles given by the user it is zero. The fixtures contain no `generate` request, no message deleted or reverted, no paging, no provider-reported non-zero cost, no API-funded route, no child session's messages (only its total) and no observed sequence gap: the event excerpt skips sequence numbers only because it is an excerpt. A passing test is not observed OpenCode execution, and a new OpenCode version needs the probes re-run before its results are relied on.
